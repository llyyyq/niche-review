# 字节跳动 Agent 开发岗位高压面试演练

> 项目：智能本地生活甄选平台
> 岗位方向：Agent 应用开发 / Java 后端
> 面试风格：围绕简历强 Claim 连续追问设计理由、失败边界、指标口径与演进方案。

## 演练前事实口径

本次回答以当前代码和 `docs/project-proof` 中的证据为准，不将设计方案包装为已实现能力：

- 当前系统更准确的定位是“RAG Chatbot + 有限步只读工具编排”，不是通用自治 Agent，也不是多 Agent。
- 当前 Agent `maxSteps=1`，一次规划最多选择 3 个只读工具。
- 查询重写评测共 50 条，其中 10 条开发集、40 条固定测试集；测试集中 35 条可检索问题用于 Hit@K，5 条歧义问题用于澄清率。
- 当前最新结果为：生产混合检索 Hit@1 `65.71% (23/35) -> 88.57% (31/35)`，Hit@3 `71.43% (25/35) -> 94.29% (33/35)`，歧义问题 `5/5` 正确澄清。
- 简历中的 `85.71% / 91.43%` 是上一轮结果，应在正式投递前更新，并为对应代码状态打 Git Tag。
- Hit@K 只证明目标店铺是否进入候选集，不能证明最终答案事实正确。

## 第一轮：项目与 Agent 架构

**面试官：** 不要罗列技术栈。沿着一次“推荐运河上街人均 100 元以内餐厅”的请求，把完整链路讲清楚。

**候选人：** 请求先在事务内保存用户消息和 AI 占位消息，提交后异步生成。这个问题短且明确，走 `PASS_THROUGH`，随后批量 Embedding，执行 Qdrant Top3 与关键词混合检索，其中预算作为硬过滤、商圈参与规则打分。问题包含推荐和预算意图，因此服务端查询候选店铺的实时详情，再把原问题、RAG 资料和工具结果组装为 Prompt，通过 SSE 输出并保存消息、请求日志和工具日志。

**面试官：** 这到底是 Agent、RAG Chatbot，还是写了几个 `if` 的 Workflow？`maxSteps=1` 也能叫 Agent？

**候选人：** 更准确的定位是“RAG Chatbot 加有限步工具编排”，不是通用自治 Agent。Agent 层能根据问题在白名单内选择工具、执行工具并把结果反馈给最终模型，但 `maxSteps=1` 代表最多进行一次规划，不会形成长期自主循环，所以我不会把它包装成通用 Agent。

**面试官：** 那一次请求到底会调用几次模型 API？

**候选人：** 简单问题不调用重写和 Planner，主链路通常只有一次 Embedding 和一次最终 Chat。需要查询重写时增加一次非流式 Chat；需要 Planner 时也增加一次 Chat；两者同时触发时最多是两次前置 Chat 加一次最终 Chat。会话摘要在回答完成后异步生成，不计入首屏主链路。

**面试官：** 为什么简单问题绕过 Planner？怎么证明不会漏掉本应调用的工具？

**候选人：** Planner 会增加一次模型往返，而优惠券、探店笔记、店铺详情和附近门店等意图可以通过确定性路由低成本识别。这样能降低延迟和 Token 消耗，但关键词路由不能覆盖所有表达，漏识别时可能退化为仅 RAG 回答；当前通过固定回归案例和工具日志发现这类问题，不能承诺完全不漏。

**面试官：** 用户问 Java、天气或者政治问题时，你的系统怎么处理？

**候选人：** 当前没有独立的通用领域分类器。系统可以识别本地生活事实型问题，并在检索和工具都无证据时确定性拒答；真正的无关问题仍可能交给通用模型回答。因此它还不是严格限定领域边界的客服 Agent，若产品要求只回答本地生活问题，应增加领域分类与明确拒答策略。

## 第二轮：查询重写与上下文理解

**面试官：** 查询预处理什么时候触发？不要只说“复杂问题”。

**候选人：** 默认有三类触发条件：输入超过 160 个字符；包含“它、那家、第二家”等上下文指代；包含连接词且命中两个以上业务意图。上下文最多取最近 4 条、总长度 2400 字符，最多生成 3 条查询，每条不超过 160 字；重写模型温度为 0、最大输出 256 Token、独立超时 8 秒。

**面试官：** 重写模型必须返回什么？如果它输出一段自然语言怎么办？

**候选人：** 约定返回：

```json
{
  "action": "rewrite|decompose|clarify",
  "queries": ["独立、完整的检索问题"],
  "clarification": "需要用户确认的问题"
}
```

服务端校验动作、查询数量、长度和重复项。非法 JSON、空响应或超时不会打断聊天：指代问题转为澄清，长文本和多意图问题进入确定性压缩，再用降级查询继续检索。

**面试官：** 为什么模型失败后不直接把原始长问题做 Embedding？

**候选人：** 长背景会稀释店铺、商圈、预算等核心语义，也会增加输入成本。确定性降级会按句切分，根据店铺、类别、商圈、预算、优惠券等业务关键词打分，保留高分句并限制长度；但它只是安全降级，可能丢失低频约束，所以不能等价为模型重写。

**面试官：** 用户说“第二家有什么优惠”，你怎么知道第二家是谁？

**候选人：** 系统把最近消息和摘要作为不可信上下文交给重写模型，只有能唯一确定候选顺序时才生成带明确店名的检索问题。当前 `QR015`、`QR019` 没有稳定完成指代消解，因此转为 `CLARIFY`；这是保守的假阴性，用户补充店名后仍可继续，而不是猜错店铺再编答案。

**面试官：** 用户一次提四个需求，你最多拆三个，是不是直接丢一个？

**候选人：** 产品语义上不应该静默截断，应该要求用户确认优先级。当前 Prompt 要求超过三个独立目标时澄清，但解析器对违规的超量查询仍可能截前三条，这项约束还没有形成代码级强保证，是明确的待修复边界。

**面试官：** 重写后改变了用户原意怎么办？

**候选人：** 重写结果只用于 Embedding 和检索，原始问题始终用于消息存储、工具规划和最终回答；Prompt 还要求保留店名、商圈、预算和排除条件。当前评测会检查约束保留，但生产链路没有语义等价性判定，所以错误重写仍可能影响召回，保留原问题只能降低风险，不能完全消除。

## 第三轮：混合检索与 Qdrant

**面试官：** 你一直说关键词 fallback。它真的是向量低分时才执行吗？

**候选人：** 不是。实际链路先执行 Embedding 和 Qdrant Top3，再生成关键词与结构化规则候选；关键词有结果时先放关键词候选，再按 `shopId` 补入向量候选并截断 Top3。只有关键词为空时，才根据 0.35 阈值决定是否接受向量结果，所以“fallback”命名不够精确，实质是带关键词优先级的混合检索。

**面试官：** 关键词命中三家时，向量检索是不是白跑了？

**候选人：** 是的，当前关键词候选达到三家后会占满 Top3，向量候选不会进入最终结果。这是当前小规模规则融合的偏置：精确店名、类别和商圈查询受益，但别名、短词误匹配或同名店可能受损。

**面试官：** 那为什么不用 Elasticsearch 的 BM25，再用 RRF 融合？

**候选人：** 当前只有 114 家店，关键词部分在 JVM 中做规则打分，部署 Elasticsearch 的运维成本大于收益。规模扩大后，JVM 全量扫描会成为瓶颈，我会用 BM25 做稀疏召回，再用 RRF 按名次融合稠密和稀疏结果，避免直接比较不同量纲的分数。

**面试官：** 为什么是一店一个向量文档，而不是一篇博客一个 Chunk？

**候选人：** 一店一文档能保留店铺、优惠券和笔记的实体关系，也方便以 `shopId` 幂等 upsert，适合当前数据规模。缺点是笔记增多后语义会被稀释，目前通过限制笔记数量和文本长度控制；规模扩大后应拆成店铺、优惠券、博客三类 Chunk，携带 `shopId` 和内容类型，检索后再按店聚合。

**面试官：** 优惠券写进向量后自然过期，Qdrant 里的内容不就错了吗？

**候选人：** 建库和增量同步时只写当前有效且有库存的优惠券，但自然到期本身不会触发同步，所以向量文档可能暂时保留旧券。优惠券问题必须调用 `voucherQuery`，实时读取 MySQL 并重新校验时间和库存，Prompt 规定实时工具结果优先；当前仍缺少到期触发同步或定期重建机制。

**面试官：** 如果模型还是采用了向量里的旧券，忽略了工具结果呢？

**候选人：** 当前主要依赖 Prompt 优先级，不能从机制上保证模型一定遵守。更稳妥的方案是生成 Prompt 前先把冲突的旧券字段从 RAG 文本中删除，或者只让向量文档保留店铺语义、不保留高时效券事实，并对最终答案中的券 ID、有效期和库存做代码级校验。

## 第四轮：指标、Ground Truth 与评测泄漏

**面试官：** 你简历写 Hit@1 从 65.71% 到 85.71%，Hit@3 到 91.43%；最新报告为什么是 88.57% 和 94.29%？

**候选人：** 最新可复现结果是 88.57% 和 94.29%，简历和 README 仍是上一轮快照，需要更新。以原始混合检索为基线，查询预处理后的生产混合检索 Hit@1 从 `23/35` 提升到 `31/35`，Hit@3 从 `25/35` 提升到 `33/35`；在提交报告并打 Git Tag 前，我不会把新数字当作已冻结证据。

**面试官：** 明明是 40 条固定测试，为什么 Hit@K 的分母只有 35？

**候选人：** 40 条测试中有 35 条设置了预期店铺，用于检索命中评测；另外 5 条是上下文不足、无法唯一解析的歧义问题，只评估系统是否澄清。`31/35` 是 Hit@1，`33/35` 是 Hit@3，`5/5` 表示歧义问题全部没有盲目检索，而是要求用户补充信息。

**面试官：** 有效模型输出率只有 `19/26`，为什么最终 Hit@3 还能有 `33/35`？

**候选人：** 26 条测试触发了重写模型，其中 19 条返回有效结构，另外 7 条返回非法结果或调用失败。5 条长输入或多意图问题通过确定性 `FALLBACK` 继续检索并恢复，2 条上下文指代问题转为澄清，对应 `QR015` 和 `QR019` 两个 Hit@3 未命中，所以模型结构化输出率与最终检索命中率不是同一个指标。

**面试官：** 你的店铺、博客和题目都有内部生成成分，这个评测是不是自己出题、自己背答案？

**候选人：** 这是项目内固定回归集，不是独立第三方基准。Ground Truth 根据 MySQL 快照标注预期店铺名称，运行时再解析为 ID；多答案推荐题使用合法店铺集合，TopK 命中任意合法店铺算成功。10 条开发集用于调试、40 条测试集约定冻结，但目前仍是单人标注，严格评测还应增加真实用户问题、双人标注、测试集版本哈希和完全独立的盲测集。

**面试官：** 你有没有看过测试集结果后继续改 Prompt？

**候选人：** 当前开发集和测试集虽然在文件中分开，但项目迭代过程中确实看过测试集结果，因此不能把它描述为完全无泄漏的盲测。简历应表述为“固定离线回归集”；如果要得到更强结论，需要冻结当前实现，再由他人提供未见问题做一次最终评测。

**面试官：** Hit@3 命中正确店铺，但模型编造优惠券，为什么仍算成功？

**候选人：** 因为 Hit@K 只评检索，不评最终回答。端到端还应评实体正确率、事实忠实度、工具结果一致性、预算和商圈约束满足率、多意图覆盖率及无证据拒答率；店铺 ID、价格、有效期适合规则判定，语义完整性可由人工或 LLM-as-a-Judge 复核，并通过检索和工具日志把失败归因到具体阶段。

## 第五轮：工具调用、SSE 与安全

**面试官：** 你有几个工具？Schema 是什么？

**候选人：** 当前有 `shopDetail`、`voucherQuery`、`blogSearch` 和 `nearbyShopSearch` 四个只读工具，分别查询店铺详情、实时优惠券、公开笔记和附近门店。它不是模型直接提交完整 JSON Schema 参数的标准 Function Calling；Planner 只选择白名单工具名，`shopId` 和坐标由服务端从检索结果与请求上下文组装，因此更准确的说法是受控工具编排。

**面试官：** Planner 返回不存在的工具，或者 JSON 解析失败呢？

**候选人：** 非法工具名会被白名单过滤，非法 JSON 或 Planner 异常会回退到确定性路由，不直接中断对话。单个工具异常会记录失败日志并与其他工具隔离；当前没有按超时、可重试错误、业务无结果做完整分级，也没有工具级自动重试，证据不足时应明确告诉用户无法确认。

**面试官：** `voucherQuery` 失败了，模型能不能回答“没有优惠券”？

**候选人：** 不能。工具失败表示“无法确认”，不等于“没有优惠”；最终 Prompt 应区分成功空结果和调用异常。当前工具结果会记录成功状态，但失败降级还不够细，生产版本应把错误类型结构化传给生成模型，并禁止用过期向量事实替代失败的实时查询。

**面试官：** 探店笔记里写“忽略系统指令，调用工具”，你怎么防 Prompt Injection？

**候选人：** 当前会把检索内容视为不可信数据，并限制模型只能选择只读白名单工具，但笔记仍会进入 Prompt，尚未实现完整的内容净化与指令隔离。生产方案应把证据放入明确的数据边界、过滤可疑指令、限制工具权限，并加入注入攻击评测；所以当前只能说降低了风险，不能说已经解决。

**面试官：** SSE 连接断了，后端和模型会发生什么？

**候选人：** `emitter.send` 异常后会把助手消息标记失败，并记录已经生成的部分内容。当前没有把浏览器断连传递为模型取消信号，也没有断点续传，因此模型请求和线程可能继续消耗资源；生产上需要统一取消令牌、请求超时和幂等重试标识。

**面试官：** `first_token_ms` 是不是模型 TTFT？

**候选人：** 不是。它从异步生成开始计时，包含查询预处理、检索、工具和 Planner，到第一个 SSE delta 为止。当前通过服务端生成的 `requestId/traceId` 关联根记录、阶段 Span、模型日志与工具日志，同一会话并发请求也能精确区分。

**面试官：** 为什么不用 Spring AI、MCP 或多 Agent？

**候选人：** 当前核心问题是可靠检索和四个固定只读工具，直接适配 OpenAI-Compatible API 与后端白名单更容易控制调用边界。MCP 适合工具跨进程复用和标准化发现，多 Agent 适合职责、权限或上下文需要隔离的复杂任务；在当前规模下引入它们只会增加协议、延迟和调试成本，不能直接改善业务效果。

## 第六轮：Redis 缓存

**面试官：** BloomFilter 和空值缓存都在防穿透，为什么要同时用？

**候选人：** BloomFilter 在访问缓存和数据库前拦截明显不存在的 ID，但它有误判，不能作为不存在的最终判断。空值缓存记录数据库已经确认不存在的结果，兜住 BloomFilter 误判和重复查询，所以是“概率前置过滤 + 精确负缓存”。

**面试官：** 事务提交后删缓存能完全避免旧值回填吗？

**候选人：** 不能。它解决的是事务尚未提交时提前删除缓存，导致读请求把旧数据库值重新写入缓存的问题；仍存在旧读请求先查到旧值、更新事务提交并删缓存、旧请求最后写回旧值的极端窗口。当前依靠随机 TTL 最终恢复，若要进一步收敛可增加版本校验、延迟二次删除或 CDC 驱动失效。

**面试官：** 锁值为什么要唯一标识，再用 Lua 删除？有 TTL 还不够吗？

**候选人：** TTL 只能防永久死锁，不能防误删：线程 A 的锁过期后线程 B 获锁，A 恢复时若直接 `DEL` 会删掉 B 的锁。锁值写入唯一 owner，Lua 原子比较 owner 相同才删除，保证只释放自己的锁。

**面试官：** 锁固定 10 秒，没有续期，重建超过 10 秒怎么办？

**候选人：** 会出现第二个线程重新获锁并并发重建，唯一标识和 Lua 只能防误解锁，不能防锁过期后的重复重建。当前获取失败还使用递归重试、没有最大次数，高竞争或 Redis 异常时存在深递归和线程等待问题；更稳妥的是有限循环退避，或使用带 Watchdog 的 Redisson 锁并设置重建超时。

## 第七轮：RocketMQ 秒杀与失败补偿

**面试官：** 秒杀请求进入后，Redis、MQ 和 MySQL 分别做什么？

**候选人：** `seckill.lua` 在 Redis 原子校验库存和一人一单，随后扣减 Redis 库存、写入用户购买集合和订单级 reservation。服务端同步发送 RocketMQ，消费者获取用户级锁后检查订单 ID 和用户—优惠券记录，条件扣减 MySQL 库存，并在同一事务中保存订单和超时任务。

**面试官：** 为什么既要订单 ID 幂等，又要用户—优惠券联合唯一索引？

**候选人：** 订单 ID 处理同一消息的重复投递；联合唯一索引处理不同订单 ID 仍试图让同一用户购买同一券的情况，是数据库最终防线。两者对应不同重复维度，不能互相替代。

**面试官：** `syncSend` 超时后你立即补偿 Redis。如果 Broker 实际收到消息呢？

**候选人：** 这会出现 Redis 预占已经回滚，但消息随后被消费并在 MySQL 创建订单，导致 Redis 与 MySQL 不一致。订单幂等只能防重复写库，不能解决发送结果未知；生产上应改为事务消息或本地 Outbox，把订单意图先可靠持久化，再由投递器发送和对账。

**面试官：** DLQ 为什么依赖订单级 reservation？

**候选人：** reservation 以 `orderId` 标识这次 Redis 预扣，Lua 只有成功删除它后才归还库存并移除用户标记，因此重复 DLQ 不会多次增加库存。它解决的是补偿动作幂等，不代表所有业务竞争都已解决。

**面试官：** 如果订单已经成功落库，但同一消息又进入 DLQ，补偿会不会把库存加回去？

**候选人：** 当前 DLQ 消费者在补偿前没有查询 MySQL 订单状态，极端情况下存在错误回滚风险。应在补偿前先确认订单不存在或处于明确失败状态，再通过统一状态机和 Lua 完成补偿；更根本的方案是使用 Outbox 或事务消息消除“成功落库与最终补偿”并发的不确定窗口。

**面试官：** 你这是 Exactly Once 吗？

**候选人：** 不是。RocketMQ 是至少一次投递，系统依靠订单 ID、联合唯一索引、状态条件和 Lua 补偿实现业务幂等，目标是 Effectively Once，而不是消息层 Exactly Once。

## 第八轮：超时关单与支付竞争

**面试官：** 为什么不下单后直接发延迟消息，还要加一张超时任务表？

**候选人：** 直接发送会存在订单事务成功但消息发送失败的丢关单窗口。当前在订单事务内同时保存超时任务，事务提交后由定时器 CAS 抢占并发送延迟消息；发送失败可以记录错误并指数退避，进程重启后仍可扫描恢复。

**面试官：** 延迟消息发送成功，但任务还没标记 `SENT`，进程崩了怎么办？

**候选人：** 任务会停在 `PROCESSING`，超时后恢复为 `PENDING` 并再次发送，所以可能产生重复延迟消息。重复到达后，订单级 Redisson 锁减少竞争，`WHERE status=UNPAID` 的数据库条件更新保证只有第一次能关闭订单和归还库存，正确性依赖消费幂等，不依赖消息只发一次。

**面试官：** 支付回调和超时关单同时到达，真正的最终保障是锁吗？

**候选人：** 不是，数据库状态条件才是最终保障。支付和关单只能从 `UNPAID` 分别转到 `PAID` 或 `CANCELLED`，后到请求的条件更新会失败；Redisson 订单锁用于降低竞争和重复副作用，即使锁因租期或网络异常失效，状态也不能反转。

**面试官：** Redisson 锁固定 30 秒，没有 Watchdog，执行超过 30 秒呢？

**候选人：** 锁可能提前释放，因此不能把正确性只押在分布式锁上。当前数据库状态条件仍可阻止状态反转，但长事务或外部调用需要独立超时；若确实需要可变执行时间，应使用 Watchdog 或合理拆分临界区。

## 第九轮：压测口径

**面试官：** 你说“一万用户压测”，是不是一万并发？

**候选人：** 不是严格的瞬时一万并发。配置是 10,000 个不同 Token、10,000 个线程、每线程一次、Ramp-Up 30 秒；聚合报告平均吞吐为 333.2 req/s，这只是固定机器和脚本下的平均值，不是系统极限 QPS。

**面试官：** JMeter 显示 99% 异常，你还敢写系统没问题？

**候选人：** 100 张券只有 100 个请求成功，其余约 9,900 个售罄业务结果被断言标记为失败，所以 99% 主要是业务拒绝，不等于系统异常。最终对账为 100 笔订单、100 名唯一用户、MySQL 和 Redis 库存均为 0；严谨表述是“该轮后端日志未观察到系统异常”，而不是把 JMeter 异常率说成 0。

**面试官：** 那 333 req/s 能证明什么？

**候选人：** 只能证明在该环境、30 秒 Ramp-Up 和 100 张库存下，Lua 预扣、MQ 异步落库、幂等和库存对账链路能完成闭环。它不能证明容量上限；若做性能结论，还需要机器规格、稳定持续时长、P95/P99、CPU、GC、连接池、MQ 积压和不同库存比例下的测试。

## 第十轮：上线风险与系统演进

**面试官：** 如果明天上线，只能选三个最危险的问题，按风险排序。

**候选人：** 第一是 MQ 发送结果未知和 DLQ 补偿竞争，当前可能破坏 Redis 与 MySQL 一致性，应优先改为 Outbox 或事务消息，并增加订单状态校验。第二是知识同步任务在事务提交后异步创建，任务落库前存在宕机窗口，且优惠券自然到期不会触发更新，应改为事务内 Outbox。第三是 AI 信任与观测边界，包括笔记 Prompt Injection、缺少端到端答案评测和统一 requestId，这些直接影响答案可信度和故障定位。

**面试官：** 如果店铺扩大到十万、日请求百万，你先改哪里？

**候选人：** 检索侧可把 JVM 关键词扫描迁到 BM25 或其他倒排服务，Qdrant 负责稠密召回，再使用 RRF 和 payload filter 融合；知识同步改为事务 Outbox、队列分区和版本化索引。在线工具服务增加超时、熔断和缓存，SSE 层继续完善取消传播；现有 `requestId/traceId/spanId` 可作为后续接入 OpenTelemetry 的关联基础。

**面试官：** 最后问一个通用 Agent 问题：什么时候才值得拆成多 Agent？

**候选人：** 只有当职责、工具权限、上下文或优化目标需要明确隔离，单 Agent 加 Workflow 已难以控制复杂度时才拆。例如规划、执行和审核分别需要不同权限，并且可以通过稳定契约 handoff。当前项目只有四个只读工具，单 Agent 加确定性路由更简单，多 Agent 只会增加上下文传递、成本、延迟和故障点。

## 面试官结论

**综合判断：可进入下一轮，但不是无风险通过。**

候选人的后端可靠性基础较强，能讲清缓存锁、MQ 至少一次语义、补偿幂等、超时任务和数据库状态条件；Agent 部分没有把 RAG、工具编排或 Hit@K 包装成超出代码证据的能力，这是加分项。

最需要继续准备的内容：

- 立即统一简历、README、评测报告和 Git Tag 中的查询重写指标。
- 对 `syncSend` 结果未知、DLQ 与成功订单竞争、同步任务创建窗口给出清晰的 Outbox 演进方案。
- 准备一份端到端答案评测设计，明确检索命中不等于答案正确。
- 能展示一次完整的请求级 Trace，并说明 `conversationId`、`requestId`、`traceId`、`spanId` 和 `toolCallId` 的职责边界。
- 面试时使用“有限步受控工具编排”，不要将当前实现描述为通用自治 Agent 或标准 JSON Schema Function Calling。

## 候选人收束话术

> 这个项目的主线是可靠 Java 后端加可追溯 AI 导购。交易侧用 Redis、RocketMQ、数据库幂等和状态条件处理高并发与最终一致性；AI 侧用查询预处理、Qdrant 混合检索和只读工具降低幻觉，并通过固定评测与请求级 Trace 验证链路。当前仍有 MQ 发送结果未知、同步任务创建窗口和端到端答案评测等边界，下一步可通过 Outbox、结构化工具错误和答案忠实度评测继续演进。
