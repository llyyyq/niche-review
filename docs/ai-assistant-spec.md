# 小众点评 AI 本地生活助手：产品与研发规格

## 1. 最终目标

在现有小众点评业务数据之上，提供一个可多轮对话的本地生活智能助手。用户可以用自然语言描述需求，系统结合真实店铺、优惠券和博客数据进行检索、推理和回答，并以流式方式展示结果。

典型问题：

> 我和朋友周末想吃火锅，预算每人 150 元，离西湖近一点，有优惠券最好。

系统应返回有真实依据的店铺推荐、推荐理由、距离和可用优惠信息；不能把不存在的店铺或优惠券当成真实数据回答。

## 2. 第一阶段 MVP

第一阶段先打通一条最小闭环：会话创建、发送消息、AI 流式回答、会话消息持久化。

本阶段范围：

- 用户可以新建会话、查看自己的历史会话、继续已有会话。
- 用户发送文本问题，后端保存用户消息。
- 后端调用大模型，并通过 Server-Sent Events（SSE）分段推送回答。
- 完成时保存完整的助手回答。
- 基础上下文只带最近 6 条已完成消息，先验证多轮理解能力。

本阶段不做：

- 向量数据库和 RAG 检索。
- 自动调用店铺、优惠券、博客等业务工具。
- 支付、下单、修改数据等写操作。
- 自动摘要、Token 统计和复杂 Agent 规划。

## 3. 目标用户与用户故事

目标用户是已登录的小众点评普通用户。

1. 用户点击 AI 助手入口，创建“周末聚餐”会话。
2. 用户提问“想吃火锅，人均 150 左右”。
3. 用户无需等待完整结果，页面逐字展示助手的回答。
4. 用户继续问“离西湖近一点”，助手能结合上一轮的“火锅”和“150 元预算”理解新需求。
5. 用户重新进入页面时，能看到自己的历史会话和聊天记录。

## 4. 最终能力边界

最终版本由以下模块组成：

| 模块 | 职责 |
| --- | --- |
| 会话与消息 | 保存会话、消息、角色、时间和状态，支持多轮对话。 |
| SSE 流式网关 | 向浏览器持续推送开始、文本片段、结束和异常事件。 |
| 上下文记忆 | 最近消息窗口加历史摘要，控制模型输入 Token。 |
| 知识库 | 把店铺、优惠券、博客等业务数据转成可检索文档。 |
| 向量数据库 | 存储文档向量，按语义检索与问题最相关的内容。 |
| RAG 编排 | 检索真实资料，组合提示词，要求模型基于资料回答。 |
| 店铺画像 | 生成菜系、消费、场景、卖点、地理位置、口碑等店铺描述。 |
| 业务工具 | 查询附近店铺、店铺详情、优惠券、博客等实时数据。 |
| 日志与指标 | 记录模型、检索、工具调用、耗时、Token 和异常。 |

## 5. 研发分期

### Phase 1：会话与流式聊天

先完成最小可用聊天闭环，不依赖向量数据库。

交付物：

- `tb_ai_conversation` 和 `tb_ai_message`。
- 会话创建、列表、详情接口。
- 用户消息提交和 SSE 聊天接口。
- 最近 6 条消息组成上下文。
- 助手消息和失败状态持久化。

验收：同一会话中，第二个问题可引用上一轮语义；刷新页面后可看到完整历史消息。

### Phase 2：知识库与 RAG

先只接入店铺数据，再逐步接入优惠券和博客。

交付物：

- Qdrant 向量数据库。
- 店铺数据转文档、切分、向量化、写入和重建任务。
- 问题向量检索 Top K 店铺资料。
- 检索结果放入提示词，并要求模型没有依据时明确说明。

验收：询问某类店铺或某一消费场景时，回答能引用数据库中实际存在的店铺信息。

### Phase 3：店铺画像与业务工具

让回答同时有语义检索能力和实时业务数据。

交付物：

- 店铺画像表或向量文档字段。
- `nearbyShopSearch`、`shopDetail`、`voucherQuery`、`blogSearch` 四个只读工具。
- 工具调用日志表 `tb_ai_tool_log`。
- 工具结果进入模型上下文。

验收：用户询问“附近”“是否有券”“最新笔记”等实时条件时，系统调用真实业务查询，而不是编造答案。

### Phase 4：记忆、成本和可观测性

让长会话稳定可控，并能定位性能问题。

交付物：

- 历史消息超过阈值后自动生成会话摘要。
- Prompt 由系统指令、会话摘要、最近消息、RAG 文档、工具结果和当前问题构成。
- 请求日志表 `tb_ai_request_log`。
- 记录检索耗时、模型首字耗时、总耗时、输入/输出 Token、工具次数和失败原因。

验收：长会话不会无限携带全部历史；可从日志判断一次慢响应是在检索、工具还是模型阶段发生。

## 6. 核心交互流程

```text
用户发送问题
  -> 校验登录和会话归属
  -> 保存用户消息
  -> 读取会话摘要和最近消息
  -> (后续) 检索知识库 / 调用只读业务工具
  -> 组装 Prompt 并调用大模型
  -> SSE 推送 message_start
  -> SSE 持续推送 delta 文本片段
  -> 保存完整助手消息
  -> SSE 推送 message_end
```

如果模型或网络调用失败：保存失败状态和错误摘要，向前端发送 `error` 事件，不能把半截回答当作正常完成消息。

## 7. SSE 事件约定

| 事件 | 含义 | 示例数据 |
| --- | --- | --- |
| `message_start` | 服务端已接受请求 | `messageId`、`conversationId` |
| `delta` | 一段模型生成文本 | `content` |
| `message_end` | 回答已完整保存 | `messageId`、`finishReason` |
| `error` | 本次生成失败 | `code`、`message` |

## 8. 数据与安全约束

- 每个会话、消息和日志都必须带 `user_id`，查询时必须校验当前登录用户归属。
- AI 工具第一期只允许读取数据；支付、创建订单、修改库存等写操作不能开放给模型。
- RAG 文档中只使用可公开展示的店铺、优惠券和博客信息，不写入密码、Token 或用户隐私字段。
- 模型回答中的店铺、优惠券事实，应优先来自检索结果或工具结果。
- 外部模型 API Key 必须只存在于忽略的本地配置或环境变量中，不能提交到 Git。

## 9. 推荐技术路线

- 后端：保留现有 Spring Boot 2.3.12 和 Java。
- 流式输出：Spring MVC `SseEmitter`。
- LLM 编排：优先使用 LangChain4j，避免大规模升级现有 Spring Boot 依赖。
- 向量数据库：Qdrant（Docker 部署）。
- 关系数据：现有 MySQL。
- 缓存与限流：复用现有 Redis、Redisson 和 Lua 能力。

## 10. 当前下一步

Phase 1 的会话、消息、归属校验和 SSE 聊天接口已经完成。当前默认使用 `mock` 模型，便于在没有 API Key 时验证完整流式链路；下一步是配置真实模型并替换 Mock 输出。
